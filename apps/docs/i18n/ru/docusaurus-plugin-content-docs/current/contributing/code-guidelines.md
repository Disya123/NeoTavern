Вклады в код NeoTavern следуют общему набору правил: строгий TypeScript,
явный контракт ошибок, документация как часть изменения и измеримые целевые
показатели производительности.

## TypeScript

- Строгий режим включён для всего кода; держите его включённым.
- Необоснованные `any`, `@ts-ignore`, non-null-утверждения и приведения
  `as unknown as` запрещены.
- На границах систем — разбор, запросы, файлы, ввод плагинов — используйте
  `unknown` и проверяйте явно, прежде чем доверять данным.
- Публичные интерфейсы раскрывают экспортируемые типы. Никогда не
  дублируйте вручную типы backend и фронтенда: общие типы API живут в
  `packages/contracts` и импортируются оттуда.
- Используйте ESM повсеместно.
- Предпочитайте небольшие функции с явными входами и выходами большим
  функциям с состоянием.

## Ошибки API

Каждая ошибка API использует стабильный, машинночитаемый конверт:

```json
{
  "code": "CHARACTER_NOT_FOUND",
  "params": { "characterId": "0193..." },
  "traceId": "01J4..."
}
```

- `code` — стабильный, машинночитаемый идентификатор ошибки; не меняйте его
  после публикации.
- `params` несёт структурированный контекст, с которым клиент или плагин
  может работать.
- `traceId` связывает ошибку с логами сервера.
- Пользовательский текст никогда не составляется на backend: фронтенд
  локализует код и параметры в текст UI.

## Документация — часть реализации

Документация — часть реализации, а не хвост, идущий после кода. Любое
изменение, влияющее на поведение пользователей или разработчиков, в том же
изменении обновляет соответствующие файлы в `docs/`. Это обязательно для:

- архитектуры и границ пакетов;
- REST API, SSE, WebSocket и схем контрактов;
- Plugin SDK, Theme SDK и слоя совместимости с наследием;
- разрешений, песочницы и модели безопасности;
- схемы SQLite, миграций, резервного копирования и восстановления;
- импорта, экспорта, файлов и кэша миниатюр;
- конвейера промптов, instruct-форматов, токенизации и контекст-шифтинга;
- адаптеров провайдеров;
- десктопной упаковки, sidecar Tauri, PWA и обновлений;
- пользовательских настроек, i18n и доступности;
- несовместимых изменений, устареваний и руководств по миграции.

Дополнительные правила:

- Каждое новое `app` или `package` поставляет `README.md`, охватывающий
  назначение, публичные точки входа, зависимости, dev-команды и ограничения.
- Публичные экспорты TypeScript и точки расширения SDK получают TSDoc, когда
  одного имени недостаточно для объяснения контракта.
- Пользовательские изменения добавляются в `CHANGELOG.md`; несовместимые
  изменения также получают руководство по миграции.
- Не документируйте нереализованные функции как готовые — помечайте их
  «экспериментальными» или «запланированными».
- Держите один источник истины на контракт и ссылайтесь на него; не копируйте
  один и тот же контракт в несколько мест.

## i18n

- Никаких захардкоженных пользовательских строк в UI-коде. Все строки
  проходят через пространства имён i18next.
- Форматируйте множественные числа, даты, числа и единицы через `Intl`, а не
  конкатенацией строк.
- Переключение языка без перезагрузки страницы; обновляйте `lang` и `dir` на
  `<html>`.
- Поддерживайте RTL-макеты.
- Плагины и темы используют изолированные пространства имён, чтобы не
  сталкиваться с приложением.
- Backend возвращает коды ошибок; фронтенд их локализует.
- Добавляйте псевдо-локальные проверки для новых экранов и проверяйте
  интерфейсы с длинными переводами.

## Целевые показатели производительности

Не регрессируйте эти показатели без явного решения:

| Показатель                                          | Бюджет       |
| --------------------------------------------------- | ------------ |
| Запуск до готового UI (эталонный ПК)                | 4 с          |
| Память backend в простое                            | 180 МБ       |
| Первая страница из 100 000 персонажей               | 300 мс       |
| Открытие чата на 10 000 сообщений до последних      | 700 мс       |
| Обновления стримингового UI                         | 30 в секунду |
| Начальный бандл фронтенда (gzip, до ленивых чанков) | 2 МБ         |

Измеряйте до и после оптимизации. Не добавляйте кэш без стратегии
инвалидации.

## Тестирование

Каждое изменение добавляет тест на соответствующем уровне: модульные тесты
Vitest, интеграционные тесты Fastify `inject()`, сквозные тесты Playwright,
визуальную регрессию тем и макетов оболочки, тесты доступности, тесты
миграций, контрактные тесты плагинов и набор совместимости с наследием.
Покрывайте ошибки и повреждённые входы, отмену запросов, повторный импорт,
миграции и откат, восстановление резервных копий, очистку кэша, отключение
плагинов, безопасный режим, большие каталоги и длинные чаты, контекст-шифтинг
на границе бюджета токенов, рендер instruct-форматов и генерацию и
инвалидацию миниатюр.

## Определение готовности

Перед пушем: `pnpm format`, `pnpm lint` с нулём предупреждений, `pnpm typecheck`,
`pnpm test` и `pnpm test:e2e` для изменений UI. Подтвердите, что
связанные документы, примеры и руководства по миграции обновлены и ссылки в
документации резолвятся.

# Этап 4 — UI/API cutover registry (working checklist)

> **Status.** Living working document for the ADR-0038 Этап-4 program on the
> `react-primary` branch: the vertical-slice registry that moves every
> production React call off `/api/v2` onto the Product Wire / Kernel plane,
> in the ТЗ §20 order, one slice per PR-sized change. Exit criteria (ТЗ
> §20 Этап 4): a repository scan finds **zero** production `/api/v2` or
> `legacyRaw()` calls, and legacy Fastify no longer owns product data.
> The ST-plugin compatibility layer is already gone (ADR-0059 Amendment 1,
> 2026-10-31); what remains legacy is the Fastify/Drizzle contour itself and
> legacy full-data import.

## 1. Slice protocol (Definition of Done per row)

Every slice follows the vertical order mandated by ТЗ §20 Этап 4:

1. **contract** — wire op(s) in `packages/contracts/src/wire/registry.ts`
   (schema, scope, idempotency, byte limits, error codes); codegen refreshed;
2. **application** — kernel handler + storage, component + integration
   tests, payload gates where the op is heavy;
3. **adapter** — host surfaces (headless remote-http) reachable; no silent
   fallbacks;
4. **UI** — `apps/web` switches to the wire path (kernel mode), legacy
   browser/sidecar mode either removed or explicitly dual-mode with an
   honest default;
5. **E2E** — Playwright path for the migrated journey (kernel mode first;
   the legacy-config quarantine only while the sidecar contour exists);
6. **remove the legacy route** — the Fastify route module row is deleted in
   the SAME slice; `docs/architecture/operations-inventory.md` and the
   `ui-legacy-surface` baseline are regenerated.

A slice may ship steps 1–5 and defer step 6 only when another panel still
shares the route; the shared route's last consumer owns its deletion.

## 4. Large-file ingestion transport — decided (ADR-0061), consumers pending

Two clusters could not be honestly ported before the wire grew a large-file
ingestion contract. Both were blocked by the same fact: wire requests are JSON
(and `assets.put`, the only byte-carrying op, admits **1 MiB**), while the
kernel is a synchronous single writer.

| Cluster | Payload                                                | Why the wire cannot carry it in one request                                                                                                      |
| ------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 8 tail  | Media ops (resolved)                                   | binary or multipart; multi-MB base64 results would blow DTO budgets                                                                              | **resolved (rounds 52–54, ADR-0063):** `providers.transcribe` takes a staged audio asset id and answers text + reported language/duration (64 MiB cap); `providers.speech` / `providers.images` stage their output as `generated-audio` / `generated-image` (8 MiB / 16 MiB caps, content addressing dedupes identical output); an adapter without the capability answers `CAPABILITY_UNAVAILABLE` instead of an empty body — `crates/runtime-kernel/tests/provider_media.rs` |
| 10      | full-data backups (`/imports/fullbackup/*`)            | multipart archive up to the legacy **4 GiB** cap; extraction is minutes                                                                          | **resolved for the read half (round 43)**: the archive rides `assets.upload.*` → `assets.upload.finish` → `imports.fullbackup.analyze`; execute still pending                                                                                                                                                                                                                                                                                                                 |
| 13      | Chat background wallpapers (`/backgrounds/*`)          | multipart upload up to the legacy **25 MiB** cap; original serving above the 4 MiB `assets.content` cap                                          |
| 21a     | Plugin blobs (`/plugins/:id/blobs*`)                   | binary bodies with an 8 MiB per-blob legacy cap; the sandbox streams them through the host session — **resolved (round 44): `plugins.blobs.begin | append                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | finish | list | read | delete`** |
| 20      | Plugin sandbox/assets (`:id/sandbox*`, `:id/assets/*`) | whole package files served to the iframe; the wire has no "raw file bytes" body type                                                             |

**Decision (2026-11-02): candidate 2, chunked upload.**
[ADR-0061](../adr/0061-large-file-ingestion.md) records why candidate 1
(host-staged path) lost: the remote Web Client's only channel is Product Wire, so
a host-staged path would force a second, non-canonical upload endpoint — exactly
the second backend surface ADR-0038 forbids for new product logic.

**Status of this section:** the CONTRACT and the kernel plane are implemented —
`assets.upload.begin|append|finish|abort` (registry **144 ops**, schema **v29**
`asset_uploads`, 5 kernel tests in `crates/runtime-kernel/tests/asset_upload.rs`,
facade `backend.assets.uploadBegin/…`). What is NOT done is the per-route work
above: each row needs its consumer (hooks, backup importer, plugin blob
reader, sandbox asset reader) rewired onto the new family — the wallpaper
picker was the first one and is now flipped (round 4, row 13). Until the
rest land, the honest state of those rows is unchanged: the React hooks
refuse in kernel mode
with a stable `UnsupportedError`, and the legacy sidecar keeps the feature. The
"transport-blocked" classification of these rows is therefore lifted to
"contract landed, consumer pending" — it is no longer a blocker that code alone
cannot move.

Per-surface note (round 5): the plugin-host capabilities these rows need
(install verification, safe mode, OAuth connection sessions) are now declared
in one auditable place — [host-surface-boundary.md](host-surface-boundary.md) /
`apps/web/src/api/hostSurfaces.ts`. That does not turn them into wire ops; it
makes the boundary explicit, fail-closed on the kernel plane, and gives the
future kernel-mode executor a single list of what it has to own before rows
19/20/21a can be flipped.

Per-surface note (round 43): row 10's _read_ half is now ported —
`imports.fullbackup.analyze` takes a staged `assetId` and walks the ZIP
read-only (11 categories, nested record counts, bounded warning sample, archive
hash). The archive's 4 GiB ceiling stops being a blocker at exactly the point
where the chunked ingestion contract hands the kernel an asset id; what remains
for the row is `imports.fullbackup.execute` (destructive, conflict policy),
the discard/direct-import variants and the `DataMigrationPanel` flip.

Per-surface note (round 55): the kernel now owns a durable plugin job queue —
`plugins.jobs.enqueue|list|get|cancel` over schema v33, with
[crates/plugin-executor](../../crates/plugin-executor) as the scheduling state
machine ([ADR-0064](../adr/0064-kernel-plugin-executor.md)). Claiming and
completing stay internal, so the host's `pluginJobs` face keeps serving live
execution (`hostSurfaces.ts`) until the executor's worker loop is enabled; that
loop is gated on ADR-0064's security-review checklist, because it is the first
component that would move a secret toward plugin code. Row 21(b) therefore moves
from "no consumer exists" to "consumer designed, execution under review".

Per-surface note (round 44): row 21a is flipped. The plugin blob store is a
first-class wire family — `plugins.blobs.begin|append|finish|list|read|delete`
(registry **150 ops**, schema **v32** `plugin_blob_uploads` + `plugin_blobs`) —
instead of a second upload endpoint: `begin` records the declared size (≤ 8 MiB
per blob), `append` stages sequential 512 KiB chunks under
`<data root>/staged-blobs`, `finish` hashes the staged file and moves the bytes
to `<data root>/plugin-blobs/<pluginId>/<sha256>.bin` (content addressing keeps
dedupe and makes the name the digest), and `read` serves bounded 256 KiB ranges
so the sandbox host can satisfy `storage.blobs.get` without an 8 MiB JSON
response. Ownership is proven twice — the `storage.blobs` grant recorded at
install _and_ the upload row's plugin — so a plugin cannot append to, finish or
read another plugin's blob even knowing its upload id or digest. The React
sandbox host (`plugins/kernel/storage.ts`) now branches: kernel plane → the
wire family, legacy plane → the legacy route, with no silent fallback in
either direction. Evidence: 7 kernel tests
(`crates/runtime-kernel/tests/plugin_blobs.rs` — content addressing, dedupe,
bounded ranges, sequential staging, grant denial, cross-plugin refusal,
64-blob quota) and 3 web tests (`plugins/kernel/storage.test.ts`).

Round 47 added the packaged evidence: `run_golden_smoke` in
`apps/desktop/src-tauri/src/lib.rs` now drives `plugins.blobs.begin|append|finish`
(the sha256 of the bytes is asserted as the blob id), `plugins.blobs.read`
(bounded range + `eof`), `plugins.blobs.list` and `plugins.blobs.delete`
(idempotent truth) through the real KernelHost envelope, and
`scripts/smoke-desktop-shell.mjs` boots the portable bundle with
`NEOTA_DESKTOP_SMOKE=1 NEOTA_KERNEL=1` and exits 0 — so the family is exercised
inside `NeoTavern_0.1.0_x64-portable`, not only by kernel-plane tests.

Per-surface note (round 46c, release-gate audit): the capability-matrix audit
found that `crates/adapters/package-verify` has **no call site outside its own
crate** — on the kernel/packaged plane nothing actually verifies a plugin
package's publisher signature before `plugins.install` records it as
`verified-publisher`; the only verifier in the product is the legacy
`apps/server/src/lib/packageTrust.ts`, which the kernel plane never calls. That
is why the matrix row `security.plugin-package-trust` was corrected to
`Implemented` (it proves the trust-RANK fence, not signature verification).
Stage 6 therefore cannot delete `apps/server` until the Tauri host adapter runs
`package-verify` at install/first-load and the packaged smoke drives it; until
then the honest reading of row 19's "install partial: host verifier" is that
the verifier exists as a crate and as legacy code, not in the packaged kernel
path.

### 4.1 Reassessment after cluster 21 part 2

The plugin secret store closed the last family that was still parked behind a
"security decision". Nothing else in the missing set is waiting on a security
model: each remaining route falls into exactly one of four buckets, and none of
them can be moved by writing code alone.

1. **Ingestion transport — RESOLVED (ADR-0061, chunked upload implemented).**
   Row 8 tail (audio/images/transcribe), row 10 (backup import), row 13
   (wallpapers), row 21a (plugin blobs) and the asset half of row 20 all need
   bytes a JSON request cannot carry; the family
   `assets.upload.begin|append|finish|abort` now carries them, so this bucket
   became ordinary per-route work ("contract landed, consumer pending", see
   §4).
2. **Host/HTTP surface by architecture, not by omission.** Row 19's install
   verifier, row 20 (git install, safe-mode file, sandbox session, package
   assets), row 21b (`pluginJobs` — the in-process sandbox executor queue) and
   row 21c (`pluginAuth` — OAuth redirects plus a server-side token-holding
   fetch proxy) all own live host handles or browser-flow state. The kernel
   owns product state; moving these in would mean the kernel becoming a job
   runner and an HTTP proxy, which the approved architecture (ADR-0038/0059,
   ТЗ 14.1) deliberately keeps out of the core.
3. **N/A because the React product never calls them.** Row 9 (connection
   profiles) and row 22 (browser-session auth) are legacy-contour surfaces;
   the canonical equivalents are already covered (`providers.config.*` +
   `providers.secrets.*` + `presets.*` for row 9, the `remote-http` pairing
   adapter for row 22). The two in-row N/As (lorebook trash restore, per-theme
   file tree) are recorded the same way.
4. **First-paint boundary.** `themes/boot` must answer before React mounts, so
   it belongs to the app bootstrap (a host concern by construction) — the
   kernel already supplies its inputs and the documented first-paint difference
   stands.

Consequence for planning: the wire-coverage program in this registry is past its
old ceiling — 112 covered / 5 partial / 48 missing, and the first bucket is no
longer blocked: chunked upload
([ADR-0061](../adr/0061-large-file-ingestion.md)) removed "the wire cannot carry
these bytes" as a reason, so those routes are now ordinary consumer work for the
following rounds. What still needs an owner decision is bucket 2: whether any
host/HTTP surface (job queue, OAuth proxy, git-install verifier, sandbox session)
should be pulled into the kernel at all. Bucket 3 stays N/A and bucket 4 stays a
documented boundary. The remaining product work on covered rows was the separate
UI-flag-flip program, which is now complete (see the note above the cluster
tables): the wire side of this registry and the UI side have both landed, so what
remains is the stage-6 deletion below.

### 4.2 Stage-6 deletion plan (what removes Fastify/Drizzle)

The legacy contour is removed as one gated step, never piecemeal, because the
public build still defaults to the sidecar while the Kernel is a Preview. The
deletion list, in the order that keeps the tree buildable:

1. **Data path first.** The one-time `app.db` → `database.sqlite` conversion
   must be verified on packaged artifacts (both a converted install and a
   rollback restore), because it is the only irreversible step. Until that
   passes, every other deletion below is unsafe.
2. **Legacy transport shims (25 `legacy-compat` sites).** `apps/web/src/api/
{backend,client,events,generate}.ts` legacy branches plus the `api-v2`
   branches inside `wireBridge.ts`; after this the browser mode has no
   transport and `isKernelMode()` loses its fallback by construction.
3. **Plugin-compat bridge (19 `plugin-compat` sites).** The sandbox host code
   that still speaks `/api/v2` (`plugins/kernel/{chat,storage,jobs,models,
workers,auth,blocks,events}.ts` and `plugins/runtime.ts`). Each site must be
   re-pointed at the kernel family it already has (`plugins.state.*`,
   `plugins.secrets.*`, `chats.messages.drafts.*`, events polling, ...) or
   retired with its host handler. Plugin jobs/auth/sandbox stay host-side per
   §4.1 bucket 2, so their bridge is the _host_ adapter, not the legacy server.
4. **Legacy routes and packages.** `apps/server` (Fastify plugins, `/api/v2`),
   the `packages/db` Drizzle layer, `better-sqlite3` usage, and the legacy
   sidecar mode in `apps/desktop/src-tauri` (`NEOTA_LEGACY_SERVER`,
   `NEOTA_DESKTOP_CHANNEL` sidecar branch).
5. **Docs and gates.** ADR-0038/0059 status update, release manifest, capability
   matrix (`Packaged` for every mandatory Desktop capability), CHANGELOG
   migration guide, and a green `pnpm test` / `cargo test` / Playwright +
   accessibility run on a build that literally cannot start the sidecar.

Nothing above may be reported as done before `fastify` and `drizzle-orm` are
absent from the dependency graph and the packaged build starts without the
`NEOTA_LEGACY_SERVER` path existing.
